# Parameterized Page Editor Design

This document defines the first architecture direction for a zero-integration web editor that loads an imported HTML text file, renders it in an isolated canvas, and exposes a floating control panel driven by an external JSON manifest.

The core boundary is strict:

- The imported page remains the rendering truth.
- The external application decides which parameters are editable.
- The editor renders controls from schema and applies only built-in DOM operations.
- The editor does not discover editable parameters on its own in v1.
- The editor does not execute arbitrary user scripts in v1.

## Goal

Support this workflow:

1. Load a local HTML text file.
2. Load a pure JSON manifest generated by an external analyzer or authoring tool.
3. Render the HTML in an isolated `iframe`.
4. Render a floating control panel from the manifest.
5. Let the user change exposed values.
6. Apply those values to the loaded page through a constrained built-in operation set.

This system is a parameterized page editor, not a general DOM inspector.

## Non-Goals

The first version does not attempt to support:

- automatic discovery of editable controls from arbitrary HTML
- arbitrary JavaScript execution in bindings
- expression evaluation or multi-step programmable transforms
- event handler editing or behavior-logic editing
- exporting a rewritten HTML file as the primary output
- cross-origin loading concerns

The imported page is a local text file, so cross-origin and remote embedding constraints are intentionally out of scope for this design.

## Core Decision

The system should use a three-part manifest:

- `schema`: parameter data shape and validation
- `ui`: panel layout and widget hints
- `bindings`: mapping from parameter fields to page selectors and built-in DOM operations

Recommended direction:

- use the browser DOM as the live preview surface
- use a schema-driven form renderer for the floating panel
- compile form values into deterministic DOM operations
- fail explicitly when selectors or operations cannot be resolved safely

This approach keeps arbitrary third-party HTML rendering native while ensuring the editable surface stays intentionally constrained.

## Runtime Architecture

The runtime is split into five layers.

### 1. Document Layer

Responsibilities:

- accept imported HTML text
- create the preview `iframe`
- write the imported document into the `iframe`
- keep editor UI isolated from page CSS and page scripts

The preview document remains the rendering truth. The editor should not build a parallel internal visual tree in v1.

### 2. Manifest Layer

Responsibilities:

- load and validate the external JSON manifest
- expose normalized `schema`, `ui`, and `bindings`
- reject malformed manifests before the user begins editing

Manifest validation must happen at load time, not lazily during `apply`.

### 3. Panel Layer

Responsibilities:

- render a floating panel from `schema` and `ui`
- show field labels, defaults, grouping, ordering, and validation feedback
- surface binding errors and apply errors at field granularity

The panel is the main editing UI. A DOM inspector-style freeform property editor is not part of this design.

### 4. Apply Engine

Responsibilities:

- resolve field values from the form state
- map each field to exactly one built-in binding operation in v1
- resolve target nodes by CSS selector
- validate all operations before committing
- apply the full batch deterministically

The engine should be transaction-like: validate first, then commit the batch. Partial silent success is not acceptable.

### 5. Session State Layer

Responsibilities:

- store current manifest
- store current parameter values
- store validation errors and last apply result
- support undo/redo at the parameter-value level when added

The session source of truth is parameter state, not direct mutation history.

## Manifest Structure

### Top-Level Shape

Recommended manifest shape:

```json
{
  "version": 1,
  "title": "Landing Page Controls",
  "description": "Editable controls for a local imported page",
  "schema": {},
  "ui": {},
  "bindings": []
}
```

### `schema`

`schema` describes parameter data and validation.

Recommended responsibilities:

- field types such as `string`, `number`, `boolean`, `object`
- titles and descriptions
- defaults
- enum choices
- validation rules such as length, range, pattern, required fields
- widget-friendly hints like `format: "color"` where supported

Example:

```json
{
  "type": "object",
  "required": ["heroTitle"],
  "properties": {
    "heroTitle": {
      "type": "string",
      "title": "Hero Title",
      "default": "Build faster"
    },
    "heroColor": {
      "type": "string",
      "title": "Title Color",
      "format": "color"
    }
  }
}
```

### `ui`

`ui` controls panel presentation.

Recommended responsibilities:

- field ordering
- grouping into sections
- widget hints
- collapsible sections
- display text overrides when needed

`ui` must not contain execution logic.

Example:

```json
{
  "order": ["heroTitle", "heroColor"],
  "sections": [
    {
      "title": "Hero",
      "fields": ["heroTitle", "heroColor"]
    }
  ]
}
```

### `bindings`

`bindings` maps fields to page operations.

Each binding should describe:

- `field`: the field path in `schema`
- `selector`: CSS selector used to find the target element
- `op`: built-in operation name
- `target`: operation-specific target, when needed
- `options`: constrained operation options

Recommended example:

```json
{
  "field": "heroColor",
  "selector": ".hero-title",
  "op": "setStyle",
  "target": "color"
}
```

In v1, one field maps to one binding operation. If the product later needs one field to affect multiple places, that should be added as an explicit new capability rather than smuggled into `options`.

## Built-In Operations

The first version should support only built-in operations. No scripting escape hatch should exist.

### Content Operations

- `setText`
  - sets `textContent`
- `setHtml`
  - sets `innerHTML`
  - should be gated carefully because it changes structure and carries sanitization risk
- `setImageSrc`
  - updates `src` on media elements that support it

### Style and Class Operations

- `setStyle`
  - sets one inline style property identified by `target`
- `toggleClass`
  - adds or removes a named class according to boolean field value or explicit option

### Attribute Operations

- `setAttribute`
  - sets a single attribute identified by `target`

### Structural Operations

- `insertNode`
  - inserts a predefined HTML snippet or manifest-provided node payload relative to a selector target
- `removeNode`
  - removes a resolved node

Structural operations are intentionally narrow in v1. Arbitrary subtree rewrites are out of scope.

## Selector Resolution Rules

The first version uses selectors only. No stable node IDs are required.

Recommended resolution rules:

- a binding selector must resolve to exactly one element by default
- zero matches is an error
- more than one match is an error
- no implicit `first()` behavior in v1

This is intentionally strict. It keeps the manifest explicit and prevents hidden broad mutations.

If future use cases need broader targeting, add explicit manifest-level controls such as:

- `match: "first"`
- `match: "all"`
- `match: "nth"`

These are not part of v1.

## Apply Pipeline

The apply flow should be:

1. Validate form data against `schema`.
2. Normalize values into the internal parameter state.
3. Resolve every binding against the current document.
4. Validate operation compatibility.
5. If any binding fails, abort the whole apply batch.
6. If all bindings pass, apply all operations in deterministic order.
7. Return a structured result with success state and field-level details.

Deterministic order should be stable across runs. The simplest rule is manifest binding order.

## Error Handling

Errors must be explicit and field-addressable.

### Selector Errors

- selector not matched
- selector matched multiple nodes

The panel should show the error on the affected field and block `apply`.

### Operation Compatibility Errors

Examples:

- `setImageSrc` applied to a non-media element
- `setText` applied where text mutation is not meaningful for the selected policy
- `setStyle` missing `target`

These should be detected before DOM mutation starts.

### Structural Errors

Examples:

- insertion anchor not found
- removal selector matched zero or multiple nodes
- malformed inserted HTML payload

These should fail the full batch.

### Manifest Errors

Examples:

- missing required top-level keys
- binding references unknown field
- unsupported operation name
- malformed `ui` shape

These should fail manifest load and prevent the editor session from starting.

## Floating Panel Behavior

The panel should be a floating editor surface layered above the page preview.

Recommended behavior:

- draggable or dockable container
- grouped fields from `ui`
- validation inline next to fields
- `Apply` action that runs the transactional batch
- `Reset` action that restores current parameter state to defaults or last committed values

The panel is allowed to remain generic in v1. Custom branded editor chrome is lower priority than manifest execution correctness.

## Security and Safety

The design intentionally avoids arbitrary script execution.

Required guardrails:

- built-in operations only
- manifest load-time validation
- optional sanitization for any HTML insertion path
- explicit rejection of unsupported operation targets

Because the source is a local HTML file, the main risk is not network origin but uncontrolled mutation power. The constrained operation set is the main safety boundary.

## Persistence Direction

The primary persisted state should be parameter values associated with a manifest, not a rewritten HTML artifact.

Recommended persisted artifacts:

- original imported HTML file
- external manifest JSON
- current parameter values JSON

Optionally, the system may also materialize a compiled patch record for internal replay, but that should not replace the parameter-state contract.

## v1 Acceptance Criteria

The first version is successful when all of the following hold:

- the editor can load a local HTML text file and a manifest
- the floating panel renders from `schema` and `ui`
- each field can drive exactly one selector-based built-in operation
- `apply` is all-or-nothing
- selector and operation failures surface as field-level errors
- repeated open-and-apply runs with the same HTML, manifest, and values produce the same result

## Open Questions Deferred

These are intentionally deferred beyond this design:

- how the external application discovers candidate editable parameters
- whether one field should drive multiple operations
- whether selector targeting needs bulk-match or nth-match modes
- whether the editor should expose freeform click-to-bind authoring tools
- whether custom widgets need richer `ui` schema conventions

Those can be added later without changing the core v1 boundary.

## Recommended Implementation Sequence

1. Build manifest validation and normalization.
2. Build preview document loading in an isolated `iframe`.
3. Build the schema-driven floating panel.
4. Build selector resolution and built-in operation execution.
5. Add transactional apply and field-level error reporting.
6. Add persistence for parameter values.

This sequence keeps the first usable milestone small and directly aligned with the approved scope.
